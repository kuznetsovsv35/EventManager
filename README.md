# Event Manager Web API application
Продвинутая разработка на C# и .NET. Проектная работа.

# Работа над проектом.
## Спринт 1.
1. Создан каркас приложения (базовая структура).
2. Создание модели событии.
3. Реализация хранилища события в памяти на основе TF Core.
4. Реализация интерфейса IEventService и объектов DTO.
5. Реализация EventsController (API контролера).
6. Реализация атрибута валидации класса модели входящих данных.
7. Подготовка к публикации проекта (мелкие правки и форматирование,, документирование кода).

## Спринт 2.
1. Создан middleware для глобального обработчика ошибок.
2. При ошибках сервис возвращает единый формат ответ JSON-объект со схемой ProblemDetails.
3. Реализовано логирование исключительных ситуаций (осуществляется глобальным обработчиком).
4. Метод GET /Events дополнены параметрами фильтрации и разбивки массива данных на страницы.
5. Фильтрация данных построена на основе создания выражений в зависимости от параметров фильтрации.
6. Фильтрация реализована в отдельном самостоятельном сервисе.
7. Добавлен самостоятельный сервис разбивки набора данных, принимающий в качестве параметра размер страницы и номер запрашиваемой страницы.
8. Дополнена документация Swagger.
9. Написаны тесты отдельно для сервисов фильтрации и разбивки на страницы, тесты манипулирования событиями, интегральные тесты.
10. Подготовка к публикации проекта (мелкие правки и форматирование, документирование кода).

## Спринт 3.
1. Добавлена в модель сервиса вторая сущность, связанная с существующей (Booking).
2. Реализован паттерн «отложенная обработка + быстрый ответ» в API (возврат HTTP-статуса 202 Accepted с заголовком Location).
3. Реализован AppBackgroundService для фоновой обработки броней.
4. Написаны unit-тесты для бизнес-логики бронирования и фонового сервиса по их обработки.
5. Подготовка к публикации проекта (мелкие правки и форматирование, документирование кода).

## Спринт 4.
1. К сущности события добавлены свойства TotalSeats (общее количество мест), AvailableSeats (число свободных мест).
2. К сущности события добавлены методы управления состоянием: TryReserveSeats(int) - попытка зарезервировать места, ReleaseSeats(int) - вернуть места в пул.
3. Конструктор сущности события имеет обязательный параметр - общее число мест (обновлен входящий и исходящий DTO).
4. Для защиты целостности данных в многопоточной среде и атомарности действий (проверка - изменения) применен механизм неблокирующей синхронизации (в виду применения асинхронных методов работы с хранилищем) на основе примитива синхронизации семафор. Реализованный механизм позволяет выполнять действия атомарно. В проекте атомарно выполняются действия проверки и резервирования мест. В фоновой службе синхронизируются методы модификации данных событий в хранилище, поскольку режим обработки очереди броней теперь параллельный.
5. Добавлено исключение, сигнализирующее о не хватки мест при бронировании. Данное исключение обрабатывается обработчиком, возвращая клиенту статус конфликта.
6. В фоновой службе из очереди выбирается все ожидающие обработки брони и запускается параллельная обработка.
7. Внешняя обработка единичной брони обернута проверкой на исключения, в случает отличного от отмены бронь автоматически отклоняется. Отклонение брони в любом случает приведет к возврату мест в пул.
8. Написаны unit-тесты на логику управления местами, тесты на изменения состояния бронирования, а также тесты на конкурирующие запросы бронирования. 

## Спринт 5 и 6.
1. Создана начальная миграция (используется для создания БД).
2. Реализованы репозитории для Event и Booking с CRUD-операциями (интерфейсы IEventRepository и IBookingRepository).
3. Реализованы интеграционные тесты с использованием PostgreSQL в Testcontainers.

# Сборка и запуск проекта.
1. Клонирование репозитория:
   ```bash
   git clone -b sprint-6 https://github.com/kuznetsovsv35/EventManager.git
   ```
2. Перейти в паку "EventManager":
   ```bash
   cd EventManager
   ```
3. Сборка проекта (целевой фреймворк net10.0):
   ```bash
   dotnet build
   ```
4. Запуск тестов.
   В проекте предусмотрены unit-тесты сервисов фильтрации и пагинации, тесты манипуляции с событиями, а также интегральные тесты функциональности сервиса управления событиями. Все тесты распределены по категориям.
   Таблица 1. Категории тестов.
   | Категория | Описание |
   |-----------|----------|
   | Filters | В категорию входят unit-тесты и интегральные тесты сервиса фильтрации. |
   | Paginator | В категорию входят unit-тесты и интегральные тесты сервиса пагинации. |
   | Service | В категорию входят тесты функций CRUD |
   | Booking | В категорию входят unit-тесты и интегральные тесты сервиса бронирования и фонового процесса обработки броней. |
   | DTO | В категорию входят unit-тесты преобразований входных данных в сущности приложения и сущностей в выходные данные. |
   | Seats | В категорию входят unit-тесты и интегральные тесты логики управления местами на событиях. |
   | Database | В категорию входят тесты схемы БД. |
   | Repositories | Тесты шаблонов репозиториев событий и броней. |

   Для корректной работы тестов необходим установленный Docker. В проекте добавлен файл сценарий установки.
   ```bash
   ./install-docker.sh
   ```

   Для запуска тестов выполнить одну из команд:
   ```bash
   # Запуск всех тестов.
   dotnet test

   # Запуск всех тестов (циклически, тесты прерываются по ошибке или по <Ctrl>+<C>).
   ./test-all.sh

   # Запуск тестов сервиса фильтрации.
   dotnet test --filter "Category=Filters"
   # или
   ./test-filters.sh

   # Запуск тестов сервиса разбивки на страницы.
   dotnet test --filter "Category=Paginator"
   # или
   ./test-pages.sh

   # Запуск тестов сервиса CRUD функциональности.
   dotnet test --filter "Category=Service"
   # или
   ./test-services.sh

   # Запуск тестов сервиса бронирования
   dotnet test --filter "Category=Booking"
   # или
   ./test-booking.sh

   # Запуск тестов логики работы с DTO
   dotnet test --filter "Category=DTO"
   # или
   ./test-dto.sh

   # Запуск тестов управления местами
   dotnet test --filter "Category=Seats"
   # или
   ./test-seats.sh

   # Запуск тестов схемы БД.
   dotnet test --filter "Category=Database"
   # или
   ./test-db.sh

   # Запуск тестов репозиториев событий и броней.
   dotnet test --filter "Category=Repositories"
   # или
   ./test-repos.sh
   ```

6. запуск приложения:
   ```bash
   # Вариант 1.
   dotnet run --project EventManager
   
   # Вариант 2 (убедиться, что у файла скрипта есть атрибут выполнения).
   ./run.sh
   ```
7. Работа с миграциями.
   # Подготовка
   Для работы с миграциями необходимо установить инструмент dotnet-ef
   ```bash
   dotnet tool install --global dotnet-ef --version 10.*
   ```
   
   # Создание миграция
   ```bash
   dotnet ef migrations add InitialCreate --project EventManager
   ```

   # Обновление БД.
   ```bash
   dotnet ef database update --project EventManager
   ```

   Примечание: поскольку миграция уже создана и хранится в проектном репозитории, после клонирования нужно только обновить БД.

8. В браузере открыть: http://localhost:5108/swagger
9. На странице можно увидеть описание API и попробовать его в деле.

# Описание API.

Таблица 2. Методы API, данные запросов/ответов, возможные ответы.
| Метод | URI | Действие | Данные запроса | Ответ | Данные ответа | Возможные ошибки |
|-------|-----|----------|----------------|-------|---------------|------------------|
|GET|/events|Получить события.|см. таблицу 3 ниже.|OK|см. таблицу 6|BAD_REQUEST|
|GET|/events/{id:uuid}|Получить событие по идентификатору id.|id - ID события|OK|см. таблицу 5|NOT_FOUND|
|POST|/events|Создать событие.|см. таблицу 4|CREATED|см. таблицу 5|BAD_REQUEST|
|PUT|/events/{id:uuid}|Обновить данные о событии.|id события, см. таблицу 4|OK|см. таблицу 5|BAD_REQUEST, NOT_FOUND|
|DELETE|/events/{id:uuid}|Удалить событие по идентификатору id.|id - ID удаляемого события|OK|см. таблицу 5|NOT_FOUND|
|POST|/events/{eventId:uuid}/book|Создать бронь для указанного события.|eventId - ID события, для которого создается бронь|OK|см. таблицу 7|NOT_FOUND, BAD_REQUEST, CONFLICT|
|GET|/bookings/{id:uuid}|Получить информацию о брони.|id - ID брони.|OK|см. таблицу 7|BAD_REQUEST, NOT_FOUND|
### Примечание: 
   В случае ошибки тело ответа представляет стандартную структуру ProblemDetails.


Таблица 3. Описание параметров запроса событий.
| Идентификатор | Тип | значение по-умолчанию | Описание |
|---|---|---|---|
|title|string|null|Подстрока, включенная в заголовок события.|
|startAt|datetime|null|Дата не раньше которой начинаются события. Отсутствия значение - момент начала не ограничен.|
|endAt|datetime|null|Да не позже которой заканчиваются события. Отсутствие значения - момент окончания не ограничен.|
|page|int|1|Номер запрашиваемой страницы данных. Отсутствие значения - первая страница.|
|pageSize|int|10|Размер страницы в элементах событий. Отсутствие значение - 10 объектов на страницу.|

Таблица 4. Структура EventInputData - входящие данные о событии для создания или обновления события.
| Поле | Тип данных | Описание |
|---|---|---|
|title|string|Заголовок события.|
|description|string|Необязательное описание события.|
|startAt|string($date-time)|Момент начала события.|
|endAt|string($date-time)|Момент окончания события.|
|totalSeats|int|Количество мест на событии.|

Таблица 5. Структура EventOutputData - информация о событии, возвращаемая сервисом.
| Поле | Тип данных | Описание |
|---|---|---|
|title|string|Заголовок события.|
|description|string|Описание события (если заполнено).|
|startAt|string($date-time)|Момент начала событии.|
|endAt|string($date-time)|Момент окончания события.|
|id|string($uuid)|Уникальный идентификатор записи о событии.|
|totalSeats|int|Общее количество мест на событии.|
|availableSeats|int|Число свободных мест.|

Таблица 6. Структура PaginateResult - результат запроса массива событий, сформированного в результате фильтрации и пагинации.
| Поле | Тип данных | Описание |
|---|---|---|
|totalCount|int|Общее количество элементов в наборе|
|values|EventOutputData[]|Массив объектов описаний событий, размещенных на запрошенной странице.|
|pageNumber|int|Номер запрошенной страницы.|
|pageCount|int|Общее число страниц.|
pageSize|int|Количество событий на запрошенной странице.|

Таблица 7. Структура BookingInfo - результат запроса создания/получения броней.
| Поле | Тип данных | Описание |
|---|---|---|
|id|string($uuid)|Идентификатор брони, по которому можно получать состояние.| 
|eventId|string(uuid)|Идентификатор события, для которого создана роль|
|status|BookingStatus{$int}|Текущий статус брони: 0-ожидание обработки, 1-подтверждена, 2-отклонена.|
|createdAt|string($date-time)|Дата/время создания брони.|
|processedAt|string($date-time)|Дата/время обработки брони.|
